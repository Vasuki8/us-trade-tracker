# Product Profile Research Navigation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Root implements; fresh independent reviewer subagents assess completed changes. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Help readers move through the existing coffee profiles, open a leading partner's comparison, and share the section they are reading.

**Architecture:** Extend the current ProductExplorer with native heading links and existing profileViewPath destinations. Keep its filter and history contracts; update copied-link state when the fragment changes. Reuse existing retained-data staging, packaging, verification and publication tools.

**Tech Stack:** Astro, React, TypeScript, existing Vitest/Testing Library/Playwright, Node 24, Python 3.12+ standard library; locked dependencies.

**Spec:** The combined design below, prepared for the owner's requested single review of design, tasks and execution permissions. This document is a proposal; it authorizes no implementation or publication until approved.

## Intended outcome and recommendation

The launch brief prioritizes a faster path from a product to a useful country comparison. The two published coffee profiles already contain history, country comparisons, changes, estimated duties, detailed observations and leading partners. ProductExplorer currently has no section navigation; its leading-partner names are plain text. Its copy controller handles popstate but does not explicitly handle hashchange. These are observable workflow gaps, rather than evidence of measured customer demand.

Recommend this bounded profile-navigation batch, explicitly deferred in the previous Canada-sharing plan. It changes existing presentation and link behavior, with no new research model. The owner requested one combined review and permissions decision, so this document combines the short design and implementation plan instead of requiring separate design and planning approvals.

Alternatives considered: Canada annual category movers could help interpret the existing table, but must remain limited to ten selected categories per direction and preserve statistical exclusions. Latest-month product rankings add less with two coffee products because the existing portfolio already supplies their monthly comparisons and matching country links. Neither alternative belongs in this batch.

Success means a reader can jump to a profile section, open a leading partner's annual comparison for the same product/direction, and copy the actual current section without changing research values or downloads. This remains a fixed historical pilot; the successive-official-release acceptance requirement stays open.

## Combined design

### Section navigation

Add a compact, wrapping native nav labelled **On this profile**, near the release strip and before the controls. Use ordinary fragment anchors, without sticky positioning, scroll tracking, routing libraries or new routes.

| Link label | Target | Availability |
| --- | --- | --- |
| Trade over time | #trade-history-heading | Always |
| Compare countries | #compare-countries-heading | Always |
| What changed? | #changes-heading | Always; existing ID |
| Estimated duties | #duties-heading | Imports only; existing ID |
| Chart data | #chart-data-heading | Always |
| Leading partners | #leading-partners-heading | Always |
| Sources | #profile-sources-heading | Always |

Add the missing IDs to the existing headings. Label the existing picker and leading-partners asides with aria-labelledby pointing to their respective headings. Give the existing provenance block a small Sources heading with its target. Each listed destination must exist exactly once in the current rendered view. Keep #selected-comparison-heading unchanged; Compare countries leads to the persistent picker adjacent to the chart, and the selected summary remains immediately below the chart. Do not add a new navigation link to that conditional heading: full-page links need targets already present in server markup.

Native links retain the current query and create the browser's ordinary fragment-history entries. They work on static Imports without JavaScript. Application handlers must not overwrite the active entry's history.state; this does not require a new native fragment entry to clone its predecessor's state. Use responsive wrapping, visible keyboard focus and modest target scroll spacing. Preserve established IDs and the public profile layout otherwise.

### Leading-partner drilldowns

Make each existing Leading partners name a native link, generated by:

`profileViewPath(release.productCode,{direction,months:12,countryCodes:[partner.code]}) + '#trade-history-heading'`

This intentionally opens a fresh one-partner view with twelve-month history and the existing default annual comparison. It replaces the prior country selection; it does not append a fourth country or inherit a monthly comparison. Add the explanation **Open a partner to view its latest-twelve-month comparison.** Keep the link's visible partner name and the current ranking's values, order, share definition and unavailable behavior.

For example, the roasted-coffee Exports link for Canada is exactly `/products/090121/?direction=exports&months=12&countries=1220#trade-history-heading`. The Imports equivalent for green coffee uses `/products/090111/?direction=imports&months=12&countries=1220#trade-history-heading`.

The target is the persistent chart heading, not the conditionally rendered selected-summary heading. Existing no-JavaScript wording continues to explain that URL selections require JavaScript and static research shows default Imports; native section movement remains usable. A partner's missing observations remain unavailable after navigation.

### Fragment-aware copied links

Distinguish fragment-only movement from a changed query in ProductExplorer's current link controller. Native fragment traversal can emit popstate as well as hashchange, so adding a hashchange listener alone is insufficient: the current unconditional popstate restore closes the manual field and clears download errors.

Track the actual last-applied location.search in a private ref, updating it during initial/full restoration and changeSelection. A popstate with the same search follows the fragment-only path; a changed search uses the existing full query restoration. Handle hashchange consistently, including a duplicate event after popstate. The fragment-only path refreshes the canonical absolute copy/manual URL from current supported filters and the browser fragment, increments the existing generation guard and clears obsolete copied-success state. If the manual field is already open, keep it open with the updated value. Fragment-only movement, including back/forward, must preserve selection, comparison period, country-picker search and download state.

Retain full restoration for genuinely changed queries and current replaceState behavior for filter edits; native fragment navigation gets its normal browser history. Do not rewrite the address on hydration, introduce new query fields, change invalid-query fallback, or normalize arbitrary user fragments. A fragment that is absent in the current direction follows ordinary browser behavior; the nav itself offers only present targets. Do not overwrite active history.state; preserve existing canonical supported-query serialization.

Delayed clipboard success or failure for an older fragment must not announce success or reopen a fallback for the new fragment, including a fragment A → B → A sequence. Cleanup invalidates in-flight results and removes both listeners. No shared hook extraction or unrelated controller refactor is required.
